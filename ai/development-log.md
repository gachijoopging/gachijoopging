### ① 환경 검증 (2026-07-30)

**한 일** — `torch`·`ultralytics`·`pillow` 를 넣고 서빙 노트북에서 네 가지를 확인했다: CUDA 인식 · `yolo26s.pt` predict · `boxes.xyxyn` 형태 · **학습 로더의 EXIF 적용 여부**.

**걸린 것** — 네 번째가 예상과 **반대**로 나왔다. [`README.md`](README.md) §3.1 은 "로더가 EXIF 를 적용하지 않는다"를 전제로 대비책(데이터셋 빌드 시 `to_upright` 정방향 저장 + EXIF 제거)을 세워 뒀는데, 실제로는 적용된다. 진짜 위험은 회전 자체가 아니라 **로더가 읽는 픽셀과 라벨 기준 크기가 어긋나는 것**이었고, 확인해 보니 어긋나지 않는다.

**결과** — 대비책은 **불필요**로 판정. 데이터셋 빌드 파이프라인에서 한 단계가 통째로 빠졌다.

| 확인 항목 | 결과 |
|---|---|
| CUDA 인식 | **OK** — RTX 4070 Laptop `sm_89`, **VRAM 8GB**, 드라이버 591.44 / CUDA 13.1. fp16 커널 실행까지 확인 |
| `yolo26s.pt` predict | **OK** — `imgsz=1024` 첫 성공. weights 는 `ai/weights/` (`.gitignore` 의 `*.pt` 가 차단) |
| `boxes.xyxyn` 형태 | **OK** — `(N, 4)` float32, 0~1. `xywhn` 을 그대로 쓰면 정확히 `(w/2, h/2)` 밀리는 것까지 실측 재현 |
| 학습 로더 EXIF 적용 | **적용됨 — 예상과 반대** (아래 근거) |
| 클라우드 학습 GPU 접속 | **미착수** — 어느 서비스를 쓸지 미정 |

학습 로더 EXIF — 근거 네 가지:

- Orientation=6 프로브(저장 240×120 가로 → 표시 120×240 세로)로 측정: `YOLODataset.load_image` 가 `(240, 120)` = **세로**를 돌려주고, 픽셀 내용도 `ImageOps.exif_transpose` 결과와 같은 위치
- `verify_image_label` 이 기록하는 `labels['shape']` 도 `exif_size` 로 EXIF 보정된 값 → **로더가 읽는 픽셀과 라벨 기준 크기가 일치**
- 적용 주체는 ultralytics 코드가 아니라 **OpenCV** 다 (`utils/patches.imread` → `cv2.imdecode`). opencv-python **4.10 · 4.12 · 5.0** 세 버전 모두 적용 확인 → 클라우드 학습 환경의 버전이 달라도 같게 동작할 근거
- 예외 1건: 잘린 JPEG 를 만나면 `verify_image_label` 이 `exif_transpose` 후 **원본 파일을 덮어써 재저장**한다(`data/utils.py:194`). 데이터셋 폴더가 조용히 수정될 수 있다

`to_upright` 왕복 검증 — 같은 사진을 ⓐ 원본 세로 ⓑ 가로 저장 + Orientation=6 → `to_upright` 두 경로로 추론해 bbox 비교: 좌표 **최대 오차 0.0013** (JPEG 재인코딩 수준). EXIF 를 무시하면 같은 사진에서 검출이 **5개 → 2개**로 줄고 좌표가 완전히 어긋났다 — 함정이 실재한다는 확인.

**이월** — `progress.md` §3.1 (버전 핀 · torch 인덱스 · FP16 지정 · weights 경로) · §3.3 (학습 로더 EXIF 확정) · §3.5 (실측값) · §5 (클라우드 학습 GPU 미정).

**걸린 것** — 함정 두 개. **둘 다 계약은 지키면서 데모에서 터질 종류**였다.

1. **워밍업이 첫 사용자를 지키지 못했다.** PyTorch 는 **스레드마다 CUDA 초기화 비용(약 810ms)을 따로** 낸다. 세마포어로 GPU 만 직렬화하면 요청이 스레드풀의 여러 스레드에 흩어져 스레드마다 그 비용을 새로 내고, 워밍업 스레드와 요청 스레드가 달라 워밍업 자체가 무의미해진다. → **GPU 작업을 전용 스레드 1개에 못 박아** 해결. 직렬화도 구조로 보장돼 락이 필요 없어졌다
2. **`rect=False` 를 명시해야 했다.** predict 기본값 `rect=True` 는 종횡비를 살린 직사각 텐서를 만들어 **가로·세로·정사각이 각각 다른 모양**이 되고, cuDNN 이 모양마다 커널을 새로 골라 **모양이 처음 나올 때마다 약 810ms** 가 붙는다. 워밍업은 한 모양만 예열하므로 데모에서 세로 첫 장이 812ms 를 맞는다. `rect=False` 면 전부 `1024×1024` 하나로 모이고, 덤으로 **학습(정사각 `imgsz=1024`)과 입력 모양이 같아진다**
3. (부수) **ultralytics 가 요청 처리 중에 `pip install` 을 돌렸다.** `PIL.Image.open` 을 몽키패치해 두고 열기가 실패하면 HEIC 로 의심해 `pi-heif` 를 설치한다 — 깨진 업로드 하나가 서버에서 pip 를 돌리고 `uv.lock` 에 없는 패키지가 생긴다. `YOLO_AUTOINSTALL=false` 로 차단 (`app/__init__.py`)

**결과**

| | 첫 요청 | 동시 8건 (첫 라운드) |
|---|---|---|
| 수정 전 | 845 ms | 5,702 ms · 1.4 req/s |
| **수정 후** | **33 ms** | **194 ms · 41 req/s** |

**이월** — `progress.md` §3.1 (`rect=False` · GPU 전용 스레드 · `YOLO_AUTOINSTALL` · 시크릿 미설정 시 기동 거부) · §3.5 (실측값) · **§6 컷라인에 2건 추가** (GPU 전용 스레드 · `predict(rect=False)`). 워밍업만으로는 첫 사용자가 안 지켜진다는 게 실측으로 드러났기 때문이다.

**2. `Unlabeled litter` 517건(11%)이 담배꽁초와 같은 크기 대역이었다.** 처음엔 "정체불명이니 `GENERAL`"이 자연스러워 보였는데, 박스 크기를 재 보니 그게 함정이었다.

| `Unlabeled litter` (517건) | **20.3 px** | **75%** |
| 전체 4,784건 | ~43 px | 43% |

`GENERAL` 로 넣으면 "작고 흐릿한 것 = GENERAL" 517건이 "작은 것 = CIGARETTE" 667건과 **이 프로젝트에서 제일 중요한 클래스에서 정면으로 부딪친다.** 학습에서 제외했다. 이미지째 버리는 안은 계산해 보고 접었다 — `Unlabeled litter` 가 있는 269장을 버리면 **다른 주석 1,314건(27%)** 을 같이 잃는다.

**3. 뚜껑을 세면 페트병 1개가 `PLASTIC` 2개가 된다.** 앱은 항목 개수를 파생 통계로 쓴다(`totalItems`·`itemCount`·`byCategory`, `docs/openapi.yaml`). 병뚜껑·팝탭·용기 뚜껑 475건(10%)을 본체와 별개로 세면 누적 기록이 부풀고, 사용자는 삭제 버튼을 더 눌러야 한다(README §3.3 이 걱정한 그 문제). 그렇다고 전부 버리면 **단독으로 떨어진 뚜껑을 영영 못 잡는다** — 실제 줍깅에서 흔하다.

측정해 보니 정확히 반으로 갈렸다. TACO 는 마스크가 있어 이 판정이 자동으로 계산된다.

|---|---|---|
| `Pop tab` | 99 | **81%** (캔에 그대로 달림) |
| `Plastic bottle cap` | 209 | 56% |
| `Metal lid` / `Plastic lid` | 87 | 40% / 30% |
| `Metal bottle cap` | 80 | **11%** (거의 단독) |
| 합계 | 475 | 49% |

그래서 **기하로 갈랐다**: 라벨된 본체 박스에 50% 이상 들어가면 제외, 아니면 본체와 같은 재질로 매핑.

**여기서 한 번 틀렸다.** 검증 스크립트가 "본체"를 이름 키워드로 추측하게 짰더니 `Toilet tube`(휴지심)를 본체로 잡고 `Aerosol`(스프레이 캔, 캡이 있다)을 놓쳐서 분포가 1건 어긋났다. 숫자보다 원인이 문제였다 — **"본체"가 어디에도 적혀 있지 않아서 ⑨ 가 다시 추측하면 또 다르게 나온다.** 전수 측정으로 실제로 부품을 품는 클래스를 뽑아 보니 `Clear plastic bottle` 96 · `Drink can` 69 처럼 닫개를 가진 용기가 대부분이었고, `Plastic straw` 9 · `Garbage bag` 2 · `Plastic film` 1 은 바닥에 겹쳐 놓인 우연이었다(봉지 위에 떨어진 뚜껑은 봉지의 부품이 아니라 별개 쓰레기다). **CSV 에 `role` 컬럼을 두어 본체 19종·부품 5종을 명시**하는 것으로 고쳤다. 추측이 끼어들 자리를 없앤 것이 수정의 요점이다.

**결과** — 60종 전부 배정, 누락·중복·오타 0 (정본 대조 스크립트로 확인). **학습 4,031 박스 / 1,500장**, 원본 4,784 중 16% 제외.

- `GLASS` 가 최소인데 그중 **54%가 `Broken glass`**(중앙 12.3px). 모델이 "유리 = 반짝이는 작은 파편"으로 배우고 멀쩡한 유리병을 못 잡을 수 있다

### ⑦ 라벨링·촬영 가이드 (2026-08-02)

**한 일** — [`docs/photography-guide.md`](docs/photography-guide.md)·[`docs/labeling-guide.md`](docs/labeling-guide.md) 2종과 TACO 예시 크롭 21장([`docs/labeling-examples/`](docs/labeling-examples))을 만들었다. ⑥ 이 §3.2 에 **판정 문장**을 세웠으니 ⑦ 은 거기에 **실물·수치·절차**를 붙이는 일이다. 겸사겸사 ⑨ 의 첫 단계인 TACO 이미지 다운로드([`scripts/download_taco.py`](scripts/download_taco.py))를 앞당겨 돌렸다.

**걸린 것** — 네 가지가 예상 밖이었다.

**1. "몇 장 찍어라"에 근거가 없었다.** 검증셋 요건에서 역산했다 — 클래스별 AP 가 안정적이려면 클래스당 최소 100 인스턴스가 필요하고(50 아래면 AP 가 한두 장에 출렁여 ⑫ 판단이 불가능), 그중 **절반 이상이 자체 촬영**이어야 지표가 데모를 예측한다. TACO 는 유럽 길거리라 담배 종류도 음료 브랜드도 다르다. 350(검증) + 700(학습) ≈ **1,050 인스턴스**, 5명이면 **1인 210개**.

**핵심은 총 장수가 아니라 클래스별 할당이다.** 눈에 띄는 대로 100장을 찍으면 꽁초와 플라스틱만 나오고 유리병은 열 개도 안 나온다. 그래서 "1인 N장"이 아니라 **"1인당 7종 × 30개"** 로 썼다.

**2. 그런데 `GLASS` 30개는 물리적으로 불가능하다.** 길에서 유리병 30개를 자연 상태로 발견할 수 없다. **연출 촬영을 허용하되 학습셋 전용**으로 갈랐다 — 실제 야외에 놓고 서서 찍고(실내·책상 위 금지: 배경·조명·각도가 실환경이면 스튜디오 사진과 결정적으로 다르다), 파일명에 `-s` 를 붙여 ⑨ 가 **검증셋에서 기계적으로 제외**한다. §4.3 이 경고한 "스튜디오 사진 혼입"과 같은 위험이라 표시 없이 섞는 선택지는 없었다.

**3. 예시 크롭이 가이드 자신의 규칙을 어겼다.** 면적 큰 순으로 골랐더니 `Food Can`(나무 책상)·`Aerosol`(사무실 책상)·`Glass jar`(흰 바닥)·`Styrofoam`(실내)이 뽑혔다 — **촬영가이드가 "안 된다"고 못박은 바로 그 스튜디오풍**이다. 면적으로 정렬하면 실내 근접 촬영이 위로 올라온다는 걸 몰랐다.

TACO 의 `scene_annotations` 에 `Indoor, Man-made` 라벨이 있어서 그걸로 걸렀다. 장면 라벨이 아예 없는 이미지도 뺐다(실외라는 근거가 없다). 면적은 **상한만** 두고(근접 촬영 차단) 하한은 거의 없앴다 — 꽁초 중앙 면적이 0.011% 라 하한을 두면 핵심 클래스가 통째로 빠진다. `Aerosol`(10건)·`Glass jar`(6건)은 실외 후보 자체가 없어 개체가 충분한 종류로 교체했다.

**4. TACO 좌표계가 EXIF 적용 후 기준이었다.** 다운로드 검증에서 **해상도 불일치 152건**이 떠서 봤더니 12/12 전부 Orientation=6 이었다 — 파일은 가로(4128×2322)로 저장돼 있고 주석은 세로(2322×4128)를 기록한다. **저장 크기로 좌표를 정규화하면 이 이미지들의 bbox 가 전치돼 에러 없이 조용히 틀어진다.** ① 에서 확인한 `exif_size` 보정과 같은 이야기가 데이터셋 쪽에서도 나온 것이다. 검증을 EXIF 적용 크기 대조로 고치니 불일치 0, 이미 받아 둔 570장도 전부 통과해 무효화가 없었다.

**환경 문제 1건** — 다운로드가 **정확히 10장마다 트레이스백 없이 죽었다.** `except BaseException` 으로도 안 잡혀 파이썬 예외가 아니었고, 네트워크만 쓰는 루프(30건)와 디스크만 쓰는 루프(120MB)는 각각 멀쩡했다. **네트워크에서 받아 디스크에 다량 기록하는 조합**이 원인이었고, 범인은 **AhnLab V3 Internet Security 9.0** 이었다 — 랜섬웨어 행위 휴리스틱에 그대로 걸린다. V3 를 끄자 50장을 0.4분에 0 실패로 받았다. 팀이 전원 Windows 라 다른 사람도 같은 데 걸릴 수 있다.

**결과** — 문서 2종 + 예시 21장(실외 실환경만, 초록 박스로 정답 박스 크기까지 보여 준다). 라벨링 가이드는 **맨 위 치트시트 한 화면**만 보고 작업하도록 짰다 — 라벨링 중에 긴 문서는 아무도 읽지 않는다.

가이드에 넣은 것 중 문서화가 아니라 **실제 사고 방지**인 항목 둘:

- **카톡·DM 전송 금지.** 리사이즈되고 EXIF 가 삭제되는데 **육안으로는 멀쩡해 보여서 발견이 늦는다.** USB 또는 Google Drive 원본만 허용
- **애매하면 라벨하지 말고 공유 → 주 1회 경계 사례 리뷰.** 가이드가 모든 경우를 커버할 수는 없고, 못 커버할 때 각자 조용히 다르게 판단하는 것이 최악이다 — 나중에 confusion matrix 를 봐도 안 보인다

**미완** — TACO 이미지 **929/1500 (3.2GB)**. 실패 571건의 내역을 보니 **485가 HTTP 429** 였다 — 워커 8개로 1500장을 한 번에 훑은 게 Flickr 레이트 리밋을 건드렸다. 재시도 백오프가 최대 10초라 429 에는 아무 소용이 없었으므로 **429 는 45초씩 늘려 쉬도록** 고치고 워커를 2개로 낮춰 재실행 중이다. 이어받기가 되니 시간을 두고 몇 번 돌리면 채워진다 → §5.

### ⑧ 라벨링 도구 세팅 · 촬영 분배 (2026-08-02)

**한 일** — 라벨링 도구를 Label Studio 로컬로 확정해 세우고, [`configs/label_studio_config.xml`](configs/label_studio_config.xml)·[`scripts/prep_labeling.py`](scripts/prep_labeling.py)·[`docs/task-allocation.md`](docs/task-allocation.md) 를 만들고 가이드 2종을 고쳤다.

**시작하자마자 ⑧ 의 절반이 사라졌다.** 라벨링을 AI 담당이 단독으로 하기로 정해졌기 때문이다. "팀원 초대"는 계정·좌석·호스팅 문제였는데 라벨러가 한 명이면 전부 없는 문제가 된다. 남은 것은 도구 세팅과 **촬영** 분배다.

**걸린 것** — 다섯 가지가 예상 밖이었다.

**1. Roboflow 1순위가 무료 좌석 2명에서 깨졌다.** README §4.2 가 Roboflow 를 1순위로 둔 근거가 "웹 기반 + 계정 초대 + 작업 분배"였는데, 무료 Public 플랜은 **좌석 2명**이고 데이터를 Roboflow Universe 에 **공개 강제**한다. 5명이 애초에 못 들어간다. CVAT Online 무료도 500MB / 태스크 10개라 사진 500장이 안 들어간다. 단독 라벨링으로 바뀌면서 이 비교 자체가 무의미해졌지만, **1순위의 근거가 실제로는 틀렸다**는 것은 기록해 둘 값이다.

**2. 일정 계산이 촬영 범위를 바꿨다.** 원안은 자체 촬영 1,050 인스턴스 / 450~500장이었다. 라벨링가이드 §5 가 스스로 정한 "한 장에 5분 이상 쓰지 마세요"를 그대로 쓰면 **20~35시간**이고, 촬영 마감 8/11 → 라벨링 마감 8/16 은 5일이라 **하루 4~7시간**이다. ⑨⑩ 과 병행이 불가능하다.

"그러면 TACO 만으로 가면 되나"를 따졌고 답은 **절반만 그렇다**였다. 학습은 TACO + AI Hub 로 갈 수 있지만 **검증셋은 안 된다.** 검증셋은 성적표이고 남은 6주의 판단(⑫ A/B · ⑮ 보정 · ⑰ `CONF_MIN`)이 전부 그 위에서 이뤄진다. TACO(유럽 길거리)로 성적을 매기면 시연(한국 길거리) 성능을 예측하지 못하고 **데모 당일 처음 알게 된다.** 주광만 시연한다는 제약은 야간 데이터 필요를 없애 주지만 조명이 아닌 갭은 그대로다 — 특히 `GLASS` 는 TACO 254건 중 54%가 깨진 유리라(⑥) 모델이 "유리 = 반짝이는 작은 파편"으로 배우고 **초록 소주병을 놓칠 위험**이 있다.

그래서 **자체 촬영을 검증셋 전용으로 축소**했다: 클래스당 50 = **350 인스턴스 / 1인 70개**, 사진 100~150장, 라벨링 **5~12시간**. 클래스당 50 은 ⑦ 이 역산한 AP 안정 하한이다. 지역 갭을 메우는 수단이 자체 촬영만은 아니라는 것도 확인했다 — **AI Hub 는 국내 데이터라 소주병·한국 캔이 있다.** 스튜디오 비중이 높아 배경은 다르지만 물체 외형은 배우고, 검증셋에만 넣지 않으면 §4.3 을 지킨다. 결국 §4.3 방침은 처음부터 맞게 서 있었고 바뀐 건 자체 촬영 목표량뿐이다.

축소 뒤에 일정을 다시 계산해서 **8/11 세션이면 충분하다**는 것도 확인했다(5일에 5~12시간 = 하루 1~2.5시간). 축소 전 기준으로 "늦어도 8/7"을 권했던 것은 과한 요구였고, **마감을 바꿀 필요가 없어졌다.**

**3. Label Studio 의 YOLO export 가 클래스를 알파벳순으로 정렬한다.** 이게 이번 작업에서 가장 중요한 실측이다. `converter.py:1245` 가 라벨을 `set` 에 담고 `1259` 에서 `sorted()` 로 번호를 매긴다 — **라벨 config 순서가 파괴된다.** 우리 계약 순서(`CIGARETTE, CAN, PLASTIC, PAPER, GLASS, VINYL, GENERAL`) 대신 `CAN, CIGARETTE, GENERAL, GLASS, PAPER, PLASTIC, VINYL` 이 나오고 **`GLASS` 가 4 대신 3** 으로 export 된다. txt 파일은 완벽히 정상으로 보인다.

설계 때 "export 인덱스를 신뢰하지 않는다"를 방어적으로 정해 뒀는데 **실제로 어긋나는 것을 확인**한 셈이다. 같은 코드 `1253` 행에 `<Label category="N">` 이 있으면 그 값을 인덱스로 쓰는 경로가 있어서, config 에 `category="0".."6"` 을 박아 순서를 고정했다 — 재실행하니 `classes.txt` 가 계약 순서로 나왔다. 그래도 **⑨ 는 이름으로 재매핑한다**: `category` 속성이 빠지거나 도구를 바꾸면 다시 조용히 어긋나기 때문이다. 좌표는 **YOLO 중심 정규화**(`x=10%,w=5%` → `cx=0.125`)로 확인했고, API 계약의 좌상단 형식과 다르다.

**4. Label Studio 가 config 파일을 cp949 로 읽는다.** `converter.py:216` 이 `io.open(config)` 을 인코딩 지정 없이 호출한다. 한글 주석을 넣어 뒀더니 `UnicodeDecodeError: 'cp949' codec can't decode byte 0xeb` 로 죽었다. **1. 마스크 처리가 범위에서 빠졌다.** README §4 는 "세그멘테이션 마스크(→bbox 자동)"라 적어 마스크→bbox 변환을 ⑨ 의 할 일로 잡아 뒀다. 그런데 `annotations.json` 의 `bbox` 필드가 **이미** 세그멘테이션의 외접 사각형이었다 — 4,784건 전부 대조해 최대 편차 1px·중앙값 0px. 계산해서 확인한 뒤에야 할 일이 없다는 걸 알았다.

**7. 왕복 검증은 좌표계 오류를 못 잡는다.** 픽셀→정규화→픽셀로 되돌려 같은 값이 나오는지 보는 검증은, 틀린 축으로 나눴다가 같이 틀린 축으로 곱하면 원래 값이 그대로 돌아온다 — 버그가 있어도 통과한다. 그래서 시각 검증(`check_dataset.py`)이 선택이 아니라 필수다. 이걸 자체로 확인하려고 Task 5 Step 4 에서 분모를 일부러 뒤집어(`width`↔`height`) 넣어 봤다 — 좌표 검사가 **794건 FAIL** 했고 그려 보니 그림이 명백히 어긋났다. 검증 도구가 실제로 버그를 잡는지까지 검증한 셈이다.

다음 세 개는 ⑦ 에서 929/1500 으로 멈춰 있던 TACO 다운로드를 마무리하는 과정에서 나왔다. 실패와 오판을 그대로 적는다.

**8. 127장의 원본이 Flickr 에서 영구 거부됐다.** `batch_8` 39장·`batch_9` 88장에만 몰려 있었다. 네 번 연속 재실행해도 이 127장만 0장이었는데, **이미 받은 파일들의 원본은 정상으로 받혔다** — 그래서 IP 차단이 아니라 그 두 업로드 배치 자체의 원본 접근이 막혔다고 판정했다. 응답 코드가 429 였던 탓에 처음엔 일시적인 레이트 리밋으로 보였을 뿐이다. 미러도 다 막혀 있었다 — Zenodo 는 우리 IP 를 403(`unusual traffic`)으로 거부했고, 그쪽 v1.0 은 2019-06 자라 2019-12 자 주석과 안 맞을 가능성이 크다. Kaggle 은 API 토큰이 있어야 접근할 수 있다. 결국 `flickr_640_url` 에 있는 secret 으로 **`_b`(장변 1024)** URL 을 만들어 복구했다 — `_h`(1600)·`_k`(2048) 는 둘 다 **410 Gone** 이라 1024 가 실제로 받을 수 있는 최대였다. 목록은 `datasets/taco/substituted.txt` (val 13·train 114).

**9. 1024 를 주석 크기로 업스케일하지 않았다.** 실측해 보니 `1024 → 3264 → 1024` 이중 리샘플이 선명도(라플라시안 분산)를 **75~82%** 로 깎았다 — 그대로 저장은 96~104% 였다. PSNR 은 41~43dB 로 양쪽이 같아서 이 지표로는 차이가 안 보이는데, **고주파만 사라진다.** 담배꽁초 중앙이 10.8px 인 이 프로젝트는 그 경계가 정확히 필요한 쪽이라 업스케일을 기각했다. 그 대신 파일 크기와 주석 크기를 대조하는 검증을 `substituted.txt` 목록의 127장에만 **비율 일치**로 완화했다. 원래 이 대조의 목적은 EXIF 전치를 잡는 것이었고, 전치된 이미지는 가로세로 비율이 뒤집히므로 완화 후에도 여전히 잡힌다 — 다만 **거의 정사각형인 사진(비율 ≈ 1)은 못 잡는다**는 구멍이 남는다. 지금 127장은 비율이 0.456~2.193 으로 그 구간에 0건이라 당장은 괜찮다.

**10. 429 백오프를 오진했다가 고쳤다.** 처음엔 45초에서 5회까지 늘렸는데(파일당 최대 11.25분), 목록을 순서대로 훑는 구조라 앞쪽 파일에서 오래 잡히면 뒤쪽 파일에는 아예 도달하지 못했다 — 실측 **0.26장/분**. 45초·5회를 5초·2회로 줄이자 **약 16장/분** (약 60배)이 됐다. "45분간 0장"을 보고 프로세스가 죽은 줄 알고 재시작한 것도 오판이었다 — 실제로는 버스트 패턴이었고, 종료한 직후에 16장이 몰려 들어왔다. **오래 기다려 한 파일을 살리는 것보다, 빨리 포기하고 목록을 여러 번 훑는 쪽이 낫다**는 게 이 데이터셋에서 얻은 교훈이다.

### ⑩ 학습 스크립트 · 첫 학습 (2026-08-03)

`scripts/train.py` 를 만들고 SSAFY GPU 서버에서 3에폭을 돌렸다. **목적은 모델이 아니라 계측**이다 — 3에폭 mAP 는 쓸 데가 없고, 대신 ⑪ 본학습의 전제가 되는 숫자 7개를 회수했다. ⑩ 을 로컬 소배치로 대체할 수 있다고 봤던 08-02 판단(`progress.md` §5)을 뒤집었다: 로컬 8GB 에서 `batch=2` 로 검증되는 것은 라벨 파싱뿐이고 그건 ⑨ 가 이미 눈으로 확인했다. 검증 안 된 것은 서버 쪽 세 가지(torch cu128 설치·4.2GB 전송·`device=1` 이웃)였고, 그걸 ⑪ 시작 시점에 처음 만나는 비용이 더 크다.

**1. VRAM 선형 모델이 34% 낮았다.** ①에서 배치 1·2·4·8 을 재고 "배치 1당 734MB, 거의 완전한 직선"으로 정리했는데, 64배 하면 46 GiB 다. **실측은 62 GiB** (ultralytics 진행줄 61.6G · `nvidia-smi` 피크 63,841 MiB). 배치당 983MB 로 역산되니 작은 배치의 기울기가 큰 배치를 예측하지 못한다. 여유 25% 를 얹어 잡은 58 GiB 가 결과적으로 실측과 가까웠던 것은 **우연**이고, 그 여유는 사실 여유가 아니었다. 이 정정이 `progress.md` §5 의 "1장 한계는 배치 약 156"도 무너뜨린다 — 983MB 기준이면 절대 한계 약 146, 여유 25% 포함 **약 114** 다.

**2. ⑪ 총시간 추정이 약 30배 틀렸다.** `experiment-log.md` §6 은 100에폭에 **20~35시간**을 예상했다. 실측 에폭당 **9.4~9.6초**(누적 27.33 → 36.91 → 46.30초)라 250에폭이면 **약 40분**이다. 원인은 계산 방식이었다 — 지난 과제의 wall clock 4.6시간에 모델 배수(3.6)와 해상도 배수(2.56)만 곱하고, **우리 학습셋이 그쪽보다 15배쯤 작다는 것을 빼먹었다.** 배수는 이미지 1장당 비용의 배수인데 장수를 안 나눴으니 틀릴 수밖에 없었다. 이미지 1장당으로 환산하면 우리 6.9ms 대 저쪽 약 8ms 로 자릿수가 맞는다.

**3. `batch=64` 결정이 로그에서 직접 확인됐다.** `optimizer: AdamW(lr=0.000909, momentum=0.9)` 로 찍혔다 — `trainer.py:1121` 의 `0.002 × 5 / (4 + nc)` 를 nc=7 로 계산한 값과 소수 6자리까지 같다. 더 중요한 건 그 다음 항이다: `weight(decay=0.0005)`. `batch=48` 이었으면 `accumulate=round(64/48)=1` 이라 `0.000375` 로 스케일돼 찍혔을 값이다. 배치 결정의 근거였던 `nbs=64` 정렬이 문서 논증이 아니라 **로그 한 줄**로 확인된 셈이다.

**4. 데이터로더는 병목이 아니었다.** 서버가 144코어·1TB RAM 인데 ultralytics 기본값은 `workers=8 · cache=False` 라 올릴 여지를 의심했다. 학습 중 GPU util 을 5초 간격으로 샘플링하니 **86~100%** 였다(에폭 경계에서만 1%로 떨어진다). 올릴 이유가 없다 — 기본값을 유지한다. 다만 47초 런을 5초 간격으로 잰 13개 표본이라 **"심한 병목은 없다"까지만 말할 수 있고** 10~20% 손실은 이 해상도로 판별되지 않는다.

**5. 안내 문구가 자기 자신을 검색에 걸리게 만들었다.** `train.py` 가 "로그에서 확인할 것"으로 `'Reducing to batch='` 를 그대로 출력했다. 그 로그에서 OOM 배치 축소를 grep 하니 **1건**이 잡혔는데, 그게 내 안내 문구였다. `out of memory` 0건으로 교차 확인해 축소가 없었음을 확정했고(따라서 62 GiB·9.4초는 `batch=64` 의 값이다), 문구에서 검색어를 빼서 개념만 남겼다. **0건과 1건을 구별할 수 없게 만드는 로그는 없는 것보다 나쁘다.**

**6. 프리플라이트가 미완성 전송을 실제로 잡았다.** 4.2GB 전송 중간에 일부러 돌려 봤다 — `train 이미지 423 · 라벨 0 · 기대 1369` 로 FAIL 하고 학습을 시작하지 않았다. 이 검사가 없으면 **423장으로 3에폭을 돌고 그럴듯한 mAP 가 나온다.** 클래스 순서 검사도 같은 이유로 둔다(⑧ 에서 Label Studio 가 알파벳순으로 매겨 `GLASS` 가 4 대신 3 으로 나간 전례).

**7. ultralytics 가 원본 JPEG 41장을 덮어썼다.** `corrupt JPEG restored and saved` 가 41건이다. ① 이 "예외 1건(잘린 JPEG는 원본 파일이 덮어써짐)"으로 적어 둔 그 동작인데, **규모가 41장**인 것은 이번에 처음 셌다. 서버 사본이라 무해하다 — 정본은 로컬이고 서버는 tar 로 받은 파생본이다. 다만 **로컬에서 학습을 돌리면 로컬 데이터셋 41장의 바이트가 바뀐다.** 학습은 서버에서만 돌린다는 규칙이 이 이유로도 필요하다.

**8. 코드를 git 이 아니라 tar 로 밀었다.** 서버는 `lab.ssafy.com` 에 닿지만(네트워크 오류가 아니라 인증 요구로 멈춘다) HTTPS 자격증명이 필요하고, 남의 vLLM 이 돌아가는 **공유 머신**이다. `~/.ssh` 키를 저장소·대화에 두지 않는다는 §5 방침과 같은 이유로 GitLab 자격증명도 두지 않는다. 대신 `tar cf - | ssh … tar xf -` 한 줄로 밀어넣는다(로컬 Git Bash 에 rsync 가 없다). 대가는 서버 코드가 git 과 어긋날 수 있다는 것 — **서버에서 코드를 고치지 않는다**로 막는다. `pyproject.toml`·`uv.lock` 은 일부러 안 보냈다: 서빙 정본이고 cu130 을 가리켜서 그대로 쓰면 이 서버에서 안 도는 torch 를 깐다.

**9. 배경 이미지 19장은 정상이다.** 라벨 스캔이 `train 1369 images, 17 backgrounds` · `val 131 images, 2 backgrounds` 로 나왔다. 파일은 있고 박스가 0인 것들 — TACO 주석이 `Unlabeled litter`·부착 부품으로 전부 제외된 이미지다. 라벨 줄 수 합계가 **train 3,680 + val 351 = 4,031** 로 ⑨ 의 `EXPECTED["total_boxes"]` 와 정확히 일치해 전송·변환이 온전함을 함께 확인했다. 검증셋의 2장은 오탐을 잡아 주는 쪽이라 두는 게 낫다.

**10. `close_mosaic` 경로를 따로 밟았다 (08-04).** 위 3에폭 런은 이 경로를 지나지 않는다 — `epoch == 3 - 20` 이 성립하지 않아 mosaic 가 끝까지 열려 있다(`trainer.py:455`). 깨지면 **본학습 230에폭째**에 드러날 자리라 `close_mosaic=1` 로만 바꿔 3에폭을 다시 돌렸다: `Closing dataloader mosaic` 출력 후 **3에폭 완주**, 예외 없음(58초). 두 가지를 일부러 하지 않았다 — ⓐ `train.py` 를 고치지 않았다(§3.1 에 "서버에서 코드를 고치지 않는다"를 방금 넣었고, 검증 대상은 우리 스크립트가 아니라 ultralytics 내부 함수다) ⓑ `experiment-log.md` §3 에 행을 만들지 않았다(학습 run 이 아니라 라이브러리 경로 검사다). 로그는 서버 `~/gachi/runs/mosaic_probe.log` 에 남겼다 — **지우지 않은 이유는 그게 유일한 증거이기 때문**이다.

### ⑫ 평가 결과 판독 + `GENERAL` A/B (2026-08-04)

- **판독을 PNG 픽셀에서 읽었다.** confusion matrix 는 그림으로만 저장되므로 숫자를 눈으로 옮겨야 했다. 검산은 **7개 열의 합이 독립적으로 아는 GT 개수(44·38·73·51·35·79·31)와 맞는지** — 전부 맞았다. 한 자리라도 잘못 읽었으면 그 열이 안 맞는다
- **"놓침이 지배적"이라고 먼저 결론 냈는데 틀렸다.** 정규화 행렬의 background 행만 보고 그랬는데, 세어 보니 전체는 정답 127 · **놓침 107 · 오분류 117** 로 비슷하다. 놓침형은 `CIGARETTE`(20 vs 2)·`GLASS`(22 vs 10) 뿐이고 `CAN`(6 vs 19)·`GENERAL`(8 vs 17)·`PLASTIC`(16 vs 27)은 오분류형이다. **정정이 오히려 ⑱ 을 갈라 줬다** — 유형이 다르면 레버가 다르다
- **P·R 로 A/B 를 비교했으면 오진했다.** 통제 실행에서 **같은 weights·같은 이미지**인데 전체 P 0.527 → 0.536 · R 0.355 → 0.375 로 움직였다. ultralytics 가 보고하는 P·R 은 클래스 평균 F1 이 최대인 지점에서 읽는 값이라 클래스 집합이 7→6 이면 그 지점이 옮겨간다. **AP 는 곡선 전체의 면적이라 소수 3자리까지 불변**이었고, 그래서 비교를 AP 로만 했다
- **`six_map50` docstring 에 사실이 틀린 근거를 적었다.** "B 가 `conf=0.001` 에서 `GENERAL` 을 뱉으면 AP 0 이 평균에 섞인다" 고 썼는데, `ap_per_class` 는 **GT 에 없는 클래스를 아예 제외**하므로 일어나지 않는다. 통제 실행 출력이 보여줘서 고쳤다 — 남겨 둘 이유는 여전히 있다(그 값의 분모가 데이터셋에 따라 7 또는 6 으로 바뀌므로 직접 세는 쪽이 자를 고정한다)

**결과** — **A(7종) 유지.** B 는 0.382 에 못 미친 정도가 아니라 A 보다 낮다.

### ⑭ 전처리 위치 결정 (2026-08-06)

**한 일** — **리사이즈를 어디로도 옮기지 않는다.** 기준(`차이 > 400ms 이면 옮긴다`)은 실측이 넘겼는데도 안 옮기기로 했다. 그 값의 구성이 기준의 전제를 무너뜨렸기 때문이다.

- **⑭ 의 입력이 애초에 0건이었다.** §4.1 #3 이 계측 로그를 "⑭ 판단의 유일한 입력" 으로 적어 뒀는데, `app.ai.base-url` 이 비면 `infer()` 가 호출을 건너뛴다(`AiInferenceClient.java:55`). 그리고 **배포 설정에는 그 값을 넣을 자리 자체가 없었다** — `infra/docker-compose.yml` 의 `x-spring` 환경 블록에도 `.env.example` 에도 `AI_BASE_URL`·`AI_SECRET` 키가 없다. §5 는 "값을 안 넣었다"로 적고 있었지만 **없던 것은 값이 아니라 배선**이다. `APP_AI_BASE_URL`·`APP_AI_SECRET` 두 줄과 `.env.example` 항목을 넣었다
- **그래서 로그 대신 curl 로 직접 쟀다.** `차이 = 총 왕복 − inferenceMs` 이고 `inferenceMs` 는 응답 본문에 있으므로, Spring 을 거치지 않고 원격 지점에서 `/internal/infer` 를 때려도 같은 값이 나온다. 빠지는 것은 Spring 의 multipart 조립분뿐이고 그건 로컬 직결 실측에서 **12ms** 다 — 400ms 판정을 흔들 크기가 아니다
- **측정 지점이 값을 정한다 — 루프백은 값이 아니라 상한이다.** 같은 서버·같은 사진인데 로컬 직결 **12ms** · 이 PC 루프백(내 PC → ngrok → 내 PC) **1,120ms** · 원격(ssafy-gpu → ngrok → 내 PC) **473ms** 다. 루프백이 두 배 이상인 이유는 1.5MB 를 **내 업링크로 한 번 더 올리기 때문**이다. §3.4 가 경계한 것은 "로컬 직결이라 무조건 400ms 아래로 나온다" 였는데, **루프백은 반대 방향으로 똑같이 못 쓴다.** 내 다운링크는 33~52MB/s 라 병목이 아니다(따로 측정)
- **차이는 사진 크기에 비례하지 않는다 — 고정비가 지배한다.** 장변 1024/1280/1536/2048(522/753/1002/1525KB)에서 **320/359/396/473ms**. 직선으로 맞추면 **240ms + 0.15ms/KB** 이고, 73KB 사진의 실측 230ms 가 절편을 뒷받침한다. 빈 봉투를 보내도 240ms 다
- **그래서 기준을 넘겼는데도 안 옮긴다.** `>400ms → 옮긴다` 는 "차이가 전송량 때문"이라는 전제로 쓰인 기준이다. 실측은 아니라고 말한다 — 장변 2048 → 1024 로 페이로드를 3분의 1로 줄여도 **버는 것은 153ms** 이고 320ms 에서 멈춘다. 400ms 밑으로 들어가긴 하지만 **원인(터널 왕복 240ms)은 그대로**다. 그 153ms 를 사자고 이중 보간 화질 손실(README §3.1 — 하필 꽁초 크기에서 드러난다)과 EXIF 보존 요구를 떠안지 않는다
- **EC2 가 아니라 SSAFY GPU 서버에서 쟀다.** EC2 SSH 키(`I15A702T.pem`)가 이 PC 에 없다 — `~/.ssh/config` 에 `ssafy-gpu` 항목뿐이다. **판정 방향은 이 대체로 안 흔들린다**: AWS 업링크가 SSAFY 망보다 빠르면 473ms 는 더 내려가 안 옮길 이유가 더 커지고, 느리면 더 올라가지만 그때도 **옮겨서 버는 건 여전히 153ms** 다. 고정비 240ms 가 클라이언트와 무관해서다
- **배포된 백엔드는 살아 있다.** 팀 쪽 이야기와 반대라 다시 확인했다 — `POST /api/v1/auth/login` 에 `{}` 를 보내면 `{"code":"VALIDATION","message":"password must not be blank","requestId":…}` 가 온다. **이 저장소의 에러 봉투에 로그인 DTO 의 Bean Validation 메시지**라 nginx·Cloudflare 가 만들 수 없다. 보안 헤더도 두 벌 찍히고(nginx + Spring Security), Spring 이 죽었다면 nginx 가 502 를 냈을 것이다. 처음에 근거로 든 401·400 은 **약했다** — 그 둘은 nginx 혼자서도 낸다. 다만 **어느 커밋인지는 밖에서 알 수 없다**(`actuator/info` 가 401)

**결과** — 전처리 위치는 지금 구조 그대로다. 앱이 장변 2048 로 줄이고(결정 35), 백엔드는 무가공 전달하고(§4.1 #2), AI 서버는 letterbox 만 한다(README §3.1). **코드는 한 줄도 안 바뀐다** — 바뀐 것은 `infra` 배선 둘뿐이다.

**아직 아니다** — 배포 환경에 `AI_BASE_URL`·`AI_SECRET` **주입은 못 했다**(EC2 접근 없음, §5). 배선만 깔았다. 주입되면 `AiInferenceClient.java:96` 의 로그로 EC2 실제 값을 볼 수 있지만 **그것으로 이 판정이 뒤집히지는 않는다** — 위 세 번째 근거 그대로다.

**이월** — `progress.md` §1 · §2(⑭ 종료) · **§3.4 전면 재작성**(열린 결정 → 확정) · §3.5(터널 전송 비용·측정 지점 함정 2행 신규) · §4.1 #3(로그가 ⑭ 의 입력이 아니게 된 경위) · §5(AI 주입 행 재작성 + **EC2 접근 없음 신규**). `infra/docker-compose.yml`(`APP_AI_BASE_URL`·`APP_AI_SECRET`) · `infra/.env.example`(AI 절 신규). 측정 스크립트는 **일회성이라 저장소에 두지 않았다**(⑬ 과 같은 이유).
