쓰레기 사진 1장을 받아 **7종 카테고리 + bbox + 신뢰도**를 돌려주는 추론 서버와, 그 모델의 학습 전 과정.

> 서빙 가중치 `weights/yolo26s-1024-v1.pt`(20MB) 와 데이터셋 기록 `datasets/*/_split.json`·`substituted.txt` 만 git 에 있다(`ai/.gitignore` 의 예외). 다른 체크포인트와 데이터셋 이미지는 학습 서버(`~/gachi/`)에 있다. 옛 모노레포 원격은 더 쓰지 않는다.

- 담당: AI 서버(FastAPI) 서빙 + 모델 학습. Spring·앱은 다른 팀원
- 기간: 6주 (2026-07-29 ~ 09-08) · 구현 1명, **라벨링은 팀 전체 투입**
- 자원: RTX 4070 Laptop(서빙) · 클라우드 학습 GPU · ngrok 무료 dev 도메인 (유료 전제 폐기 — 진행상황.md §3.1, 확정 08-04)

```
앱 ──사진──▶ Spring ──원본 그대로──▶ FastAPI (ngrok) ──▶ YOLO26s @ 4070
             │                      EXIF 회전 + 추론          │
             ◀──────── items ────────────────────────────────┘
앱 ◀── url, thumbUrl, inference ──┘
```

앱은 FastAPI를 직접 호출하지 않습니다. **추론 실패가 사진 업로드를 실패시키지 않고**, `inference.status = UNAVAILABLE` → 앱이 수동 입력으로 내려갑니다.

**관련 문서** — 앱·백엔드 API 계약은 [`docs/openapi.yaml`](../docs/openapi.yaml), 백엔드 구조는 [`docs/백엔드/01-구조.md`](../docs/백엔드/01-구조.md), 진행 상태는 [`진행상황.md`](진행상황.md), 학습 이력은 [`실험기록.md`](실험기록.md), 끝난 작업의 근거·과정은 [`개발일지.md`](개발일지.md).

"모델 학습 → 정확도 확보 → 그다음 서빙"으로 가면 3주 뒤 서빙을 붙이다 bbox 좌표계·EXIF·타임아웃에서 전부 터지고, 그동안 Spring·앱은 아무것도 못 합니다.

4. 트래픽 보내기 전 `/healthz`로 준비 확인

## 2. AI 서버 계약

앱이 직접 호출하지 않으므로 Spring과의 사내 계약입니다.

```
POST /internal/infer
X-AI-Secret: <shared secret>
Content-Type: multipart/form-data
  file: 원본 JPEG (가공 없음)

200 { "modelVersion": "yolo26s-1024-v1",
      "inferenceMs": 94,
      "items": [ { "bbox": {"x":0.31,"y":0.44,"w":0.12,"h":0.09},
                   "category": "CIGARETTE", "aiConfidence": 0.93 } ] }

401  { "code": "UNAUTHORIZED" }     시크릿 불일치
422  { "code": "INVALID_IMAGE" }    이미지로 열 수 없음 (JPEG 아님·손상)
422  { "code": "VALIDATION" }       file 필드 누락
503  { "code": "AI_UNAVAILABLE" }   모델 미로드 또는 워밍업 미완료

GET /healthz → { "ready": true, "modelVersion": "…", "warmedUp": true, "error": null }
               준비되면 200, 준비 전·로드 실패면 503. 본문 형태는 같고 `error` 에 원인이 담깁니다.
               시크릿을 요구하지 않습니다 (GPU 를 쓰지 않고 §9 에서 curl 로 확인하는 용도).
```

에러 본문은 전부 `{"code", "message"}` 한 형태입니다. **백엔드는 200 이외를 전부 `UNAVAILABLE` 로 바꾸면 되므로** `code` 를 분기에 쓸 필요는 없습니다 — 로그에 남겨 두면 원인 추적이 됩니다.

계약 확인은 `uv run python scripts/smoke.py` 로 자동화돼 있습니다. `--base-url` 로 원격 주소에도 그대로 겨눌 수 있어 데모 직전 점검(§9)에 씁니다.

**이 `503 AI_UNAVAILABLE`은 내부 계약입니다.** 백엔드가 이걸 받아 앱에게는 `POST /media` 응답의 `inference.status: "UNAVAILABLE"`로 바꿔 전달합니다 — 앱은 503을 보지 않습니다(`docs/openapi.yaml`의 `/media`).

`/healthz`가 있는 이유: ① 백엔드가 2~3초 타임아웃을 기다리지 않고 즉시 `UNAVAILABLE`을 판정할 수 있고 ② 데모 직전에 노트북·ngrok·모델 상태를 curl 한 번으로 확인할 수 있습니다.

`inferenceMs`는 JPEG 디코딩·EXIF 회전·letterbox·추론·좌표 변환을 포함하고 **네트워크를 제외**합니다.

## 3. 함정 세 개 — 여기가 실제 위험 지점

### 3.1 전처리는 EXIF 회전 하나뿐입니다

신경망은 고정 크기 정사각형만 받습니다. `imgsz=1024`는 입력 텐서가 문자 그대로 1024×1024×3이라는 뜻이고, 폰 사진은 4032×3024이므로 누군가는 변환해야 합니다. YOLO는 **letterbox**(종횡비 유지 축소 + 회색 패딩)를 씁니다.

**직접 리사이즈하지 않습니다.** Ultralytics가 어차피 또 letterbox를 하므로 이중 보간으로 화질만 잃고, 학습 이미지보다 서빙 이미지가 살짝 흐려집니다 — 담배꽁초처럼 작은 물체에서 드러날 수 있는 지점입니다. 무엇보다 **전처리를 손으로 만지면 좌표 역변환도 손으로 하려는 유혹이 따라오고**, 그때 letterbox 패딩을 빼는 단계를 잊으면 박스가 "대충 그 근처"에 그려져서 발견이 한참 늦습니다.

정답은 **정방향 이미지를 그대로 넘기고 `imgsz=1024`를 predict 인자로 주는 것**입니다. letterbox와 역변환을 라이브러리가 학습과 동일한 코드로 처리합니다.

> **W1 ② 추가 발견 — `rect=False`를 명시해야 합니다.** predict의 기본값은 `rect=True`라서 letterbox가 정사각이 아니라 **종횡비를 살린 직사각 텐서**를 만듭니다: 가로 사진 → `(1024, 768)`, 세로 → `(768, 1024)`, 정사각 → `(1024, 1024)`. cuDNN은 텐서 모양마다 커널을 새로 고르므로 **모양이 처음 나올 때마다 약 810ms**가 붙고, 워밍업은 한 모양만 예열하니 **데모에서 세로 첫 장이 812ms를 맞습니다.** `rect=False`면 모든 입력이 `1024×1024` 하나로 모여 21~38ms로 평탄해지고, 덤으로 **학습(정사각 `imgsz=1024`)과 입력 모양이 같아집니다.** 스케일은 양쪽 동일하고 회색 패딩 양만 달라 정확도 영향은 없습니다.

```python
# preprocess.py — 학습 스크립트와 서빙이 함께 import 하는 유일한 전처리
from PIL import Image, ImageOps

def to_upright(img: Image.Image) -> Image.Image:
    """EXIF Orientation을 픽셀에 적용한 정방향 RGB 이미지."""
    return ImageOps.exif_transpose(img).convert("RGB")
```

이 파일이 "학습 전처리와 서빙 전처리가 동일한 코드 경로를 쓴다"는 요구사항의 실체입니다. 리사이즈는 Ultralytics가 양쪽에서 동일하게 하므로 맞춰야 하는 건 EXIF 회전 하나입니다.

> **W1 ① 확인 완료 (07-30)**: Ultralytics 8.4.112 학습 로더는 **EXIF를 픽셀에 적용합니다.** 적용 주체는 ultralytics 코드가 아니라 `cv2.imdecode`(opencv-python 4.10·4.12·5.0 공통 확인)이고, 라벨 검증이 기록하는 이미지 크기도 `exif_size`로 보정돼 **로더가 읽는 픽셀과 어긋나지 않습니다.** 따라서 데이터셋 빌드 시점의 정방향 재저장은 **하지 않습니다.** 근거와 예외 1건(잘린 JPEG는 원본 파일이 덮어써짐)은 [`개발일지.md`](개발일지.md) ①.

### 3.2 bbox는 `xyxyn`을 씁니다

| 속성 | x, y 의 의미 | 단위 |
|---|---|---|
| `boxes.xyxy` | 좌상단 + **우하단 꼭짓점** | 픽셀 |
| `boxes.xyxyn` | 좌상단 + **우하단 꼭짓점** | **0~1** |
| `boxes.xywh` | **중심점** + 너비·높이 | 픽셀 |
| `boxes.xywhn` | **중심점** + 너비·높이 | 0~1 |

API가 요구하는 것은 `{x: 좌상단x, y: 좌상단y, w, h}` 0~1 정규화입니다. **함정은 `xywhn`이 이름만 보면 완벽히 일치한다는 것** — 네 글자가 같고 단위도 같은데 x, y의 뜻이 다릅니다. 그대로 꽂으면 에러가 안 나고 박스만 `(w/2, h/2)`씩 우하단으로 밀립니다.

`xyxyn`은 정의상 두 꼭짓점이라 "중심"으로 해석될 수가 없습니다. 그래서 변환이 산수로 끝납니다.

> **W1 ③ 검증 완료** — `scripts/draw_boxes.py` 가 **서버 HTTP 응답의 `{x,y,w,h}` 만으로** `to_upright` 적용 이미지에 박스를 그립니다. 둘 다 의도적입니다: ultralytics 의 `result.plot()` 을 쓰면 라이브러리 내부 좌표로 그려져 **변환 버그가 그림에서 사라지고**, EXIF 를 적용한 이미지에 그려야 앱 화면과 같은 조건입니다. `--show-center-bug` 는 같은 숫자를 중심점으로 해석한 박스를 빨간색으로 겹쳐 그려 함정을 한 장으로 보여 줍니다.

```python
for (x1, y1, x2, y2), cls, conf in zip(b.xyxyn.cpu().numpy(),
                                       b.cls.cpu().numpy(),
                                       b.conf.cpu().numpy()):
    items.append({
        "bbox": {"x": float(x1), "y": float(y1),
                 "w": float(x2 - x1), "h": float(y2 - y1)},
        "category": CLASSES[int(cls)],
        "aiConfidence": float(calibrate(conf)),      # §6
    })
```

### 3.3 임계값이 **두 개**입니다

| 값 | 역할 | 결정 시점 |
|---|---|---|
| `CONF_MIN` | 이 값 미만은 `items`에 넣지 않음 | W4 실측 |
| `0.7` | `unclassified` — 사용자 확인 요구 | API 계약. 유지 |

모델은 사진 한 장마다 후보 박스를 **300개 고정으로** 뱉습니다(NMS-free). 대부분 confidence 0.01짜리라 어딘가에서 잘라야 합니다.

```
후보 300개
  ├ conf < CONF_MIN        → 응답에 안 넣음. 앱은 존재조차 모른다
  ├ CONF_MIN ≤ conf < 0.7  → 넣고 unclassified = true  (사용자 확인)
  └ conf ≥ 0.7             → 넣고 unclassified = false (확인 없이 통과)
```

- Ultralytics 기본값 0.25를 쓰면 사진마다 오탐이 5~6개 → **25장 활동에서 삭제 버튼을 100번 넘게 누릅니다**
- `CONF_MIN`을 0.7로 잡으면 모든 항목이 0.7 이상이라 **`unclassified`가 영원히 false** → API의 사용자 확인 플로우 전체가 죽은 코드가 됩니다

그래서 `CONF_MIN < 0.7`이어야 하고, W4 reliability diagram에서 **정밀도가 대략 50%가 되는 지점**을 시작점으로 잡습니다.

### 4.4 `GENERAL` — **7종 유지로 확정 (⑫, 08-04)**

원래 걱정은 *"시각적 일관성이 없어 다른 6종의 오탐을 빨아들일 위험"* 이었고, A(7종 학습) vs B(6종 학습 + 나머지는 사용자 수동 지정)를 실험으로 가르기로 했습니다. **A 를 유지합니다.**

**전제부터 틀렸습니다.** confusion matrix 에서 예측 `GENERAL` 이 다른 6종 GT 320개에서 가져간 것은 **12개(3.7%)** 뿐이고 배경 오탐 몫도 밑에서 두 번째입니다. 빨아들이는 쪽은 **`VINYL`** 이었습니다(진짜 `GENERAL`·`PAPER`·`PLASTIC`·`CAN` 을 18~26%씩). `GENERAL` 은 포식자가 아니라 피해자입니다 — GT 31개 중 정답 6개.

**그래도 B 를 돌렸고, B 가 졌습니다.** 판정선(6종 mAP50 이 A + 0.03 = 0.382 이상이면 채택)을 돌리기 전에 못박고 실행했습니다. 결과는 **A 0.352 vs B 0.344** 로 A 보다 낮고, 결정적으로 `unclassified` 비율이 **45.4% → 62.7%** 로 악화됩니다. `GENERAL` 244개를 지우면 그 물체들이 배경 supervision 이 되어(배경 이미지 17 → 89) 6종 확신까지 눌립니다. 숫자와 근거는 [`실험기록.md`](실험기록.md) §4 `run: train_nogen`.

> 설계에서 **`nc` 를 6으로 줄이지 않고 7을 유지한 채 `GENERAL` 라벨만 제거**한 것이 이 실험을 성립시켰습니다. 그래야 서빙 코드(`app/classes.py`)를 안 건드리고, **같은 평가 스크립트로 A 를 다시 재는 통제 실행**이 가능합니다. 실제로 그 통제 실행이 "검증 라벨에서 `GENERAL` 을 빼도 6종 AP 는 소수 3자리까지 불변"임을 확인해 줬습니다.

## 5. 학습

### 모델: `yolo26s`, `imgsz=1024`

YOLO26의 **STAL**(작은 객체 positive label 커버리지 유지)이 담배꽁초에 직결되고, **NMS-free**라 후처리 없이 `(N, 300, 6)` 직접 출력이라 서빙이 단순합니다.

| 모델 | params | FLOPs | COCO mAP | T4 지연 |
|---|---|---|---|---|
| yolo26n | 2.4M | 5.4B | 40.9 | 1.7ms |
| **yolo26s** | **9.5M** | **20.7B** | **48.6** | **2.5ms** |
| yolo26m | 20.4M | 68.2B | 53.1 | 4.7ms |
| yolo26l | 24.8M | 86.4B | 55.0 | 6.2ms |

4070은 T4보다 빠르므로 `x`조차 실시간입니다 — **연산은 제약이 아닙니다.** 실제 제약은 데이터 양이고, 수천~1만 장에서 `m` 이상은 과적합 위험이 큽니다.

**파라미터보다 해상도에 예산을 씁니다.** 같은 연산량이면 `s@1024`가 `m@640`보다 이 도메인에서 낫습니다. 담배꽁초는 사진에서 차지하는 픽셀이 극히 작아 탐지 성능이 입력 해상도에 지배되기 때문이고, 이것이 **온디바이스(저사양 기기 때문에 640으로 내려야 함)를 포기하고 서버 추론을 택한 이유**입니다.

```python
model = YOLO("yolo26s.pt")          # COCO 사전학습에서 전이학습
model.train(data="trash.yaml", imgsz=1024, batch=64,
            epochs=250, patience=50, close_mosaic=20, device=1)
```

`imgsz=1024`가 추론과 반드시 동일해야 하는 것이 **유일한 절대 조건**입니다.

**실험 기록을 처음부터 남깁니다.** AI 작업은 "지난주 그 모델이 뭐였지?"가 서버 작업보다 훨씬 자주 발생합니다. 형식과 이력은 [`실험기록.md`](실험기록.md).

`modelVersion` 문자열이 이 기록의 외부 식별자입니다. **weights 또는 보정 맵이 바뀌면 반드시 증가시킵니다** — 사용자 활동 기록에 남는 값이라 "이 통계는 어느 모델이 만든 건가"에 답할 수 있어야 합니다.

### 평가

mAP만 보지 말고 **confusion matrix**를 봅니다. ⑫에서 실제로 읽었고, 예상 두 개 중 하나만 맞았습니다.

- **`PLASTIC`↔`VINYL` 은 남았습니다** (0.18 / 0.08). 예상대로입니다
- **`PLASTIC`↔`GLASS`(투명 페트 vs 유리병)는 기각됐습니다.** `GLASS`→`PLASTIC` 한 방향(0.09)만 있고 반대는 0입니다 — `GLASS`가 애초에 예측되지 않아 혼동이 생길 기회가 없습니다
- **예상에 없던 것이 더 컸습니다: `VINYL`이 오분류의 싱크입니다.** 예측 `VINYL`은 맞춘 37 vs 다른 클래스에서 끌어온 44이고, 진짜 `GENERAL`·`PAPER`·`PLASTIC`·`CAN`을 18~26%씩 가져갑니다
- **놓침과 오분류가 거의 같은 크기입니다** (GT 351개 중 정답 127 · 놓침 107 · 오분류 117). 클래스마다 유형이 갈리고 **유형이 갈리면 레버가 갈립니다** — 놓침형(`CIGARETTE`·`GLASS`)은 데이터 양이, 오분류형(`CAN`·`GENERAL`·`PLASTIC`)은 클래스 경계가 고칩니다

판독 전문은 [`실험기록.md`](실험기록.md) §4 `run: train`, 목표 지표는 같은 파일 §6입니다.

## 6. confidence 보정

`unclassified` 판정이 `aiConfidence < 0.7`인데 딥러닝 모델은 기본적으로 과신합니다. 실제 정확도 60%인데 0.95를 뱉으면 임계값이 무의미해지고 틀린 결과가 사용자 확인 없이 통과합니다.

**temperature scaling은 softmax 분류기용 기법이라 탐지 모델에 그대로 맞지 않습니다.** 탐지에서는 예측이 정답인지 아닌지 자체가 IoU 매칭으로 결정되기 때문입니다. 실제로 필요한 것:

1. **매칭 스크립트** — 검증셋에서 각 예측을 GT와 IoU≥0.5로 매칭해 TP/FP 라벨링 *(← 일의 90%)*
2. **reliability diagram** — confidence를 10개 bin으로 나눠 bin별 실측 정밀도 측정
3. **보정 맵** — raw confidence → 실측 정밀도의 단조 매핑을 `sklearn.isotonic.IsotonicRegression`으로 학습
4. 서빙 `calibrate()`에 반영

**보정된 값을 `aiConfidence`로 응답합니다.** 임계값 0.7을 실측값으로 바꾸는 대안도 있지만 0.7은 이미 앱·API 문서·백엔드 3곳에 박혀 있습니다. 보정 쪽을 택하면 FastAPI 안에서만 끝나고, `aiConfidence 0.7`이 **"70% 확률로 이 라벨이 맞다"는 실제 의미를 갖게 됩니다.**

예상 소요는 반나절~1일입니다. 산출물인 reliability diagram은 **발표 자료에 넣기 좋은 그림**입니다.

- 의존성은 `pyproject.toml`. 포맷터는 **ruff** (`ruff check`)
- `.gitignore`가 `*.pt`·`datasets/`·`runs/`를 차단합니다. **예외는 서빙 weights 하나뿐입니다** — `weights/yolo26s-1024-v1.pt`만 추적해, 서빙 노트북이 `git pull`만으로 모델을 갖게 합니다. 데이터셋과 나머지 체크포인트는 여전히 커밋하지 않습니다. **다음 버전에서 예외를 늘리지 않습니다** — 체크포인트가 쌓이면 clone 비용이 계속 커지므로 그때 LFS나 릴리스 첨부로 옮깁니다
- `ai/`는 CI 경로 트리거에서 제외돼 있습니다(담당자 영역)

```
uv run uvicorn app.main:app --reload     # 개발
uv run uvicorn app.main:app              # 운영 (워커 1개)
uv run python scripts/smoke.py           # 계약 확인
uv run python scripts/draw_boxes.py 사진.jpg   # bbox 위치를 눈으로 확인
```

시크릿은 `ai/.env`(커밋 안 함)에서 자동으로 읽습니다 — `.env.example` 참고. **`AI_SECRET`이 없으면 서버가 뜨지 않습니다**(터널 URL은 공개이므로 실수로 무인증 상태가 뜨는 쪽이 더 위험합니다).

**동시성** — FastAPI에서 `async def` 안에 blocking GPU 작업을 넣으면 이벤트 루프가 막혀 요청이 한 줄로 섭니다. **엔드포인트를 `def`(non-async)로 정의**하면 스레드풀에 위임되어 JPEG 디코딩이 병렬화됩니다. 4070에서 `s@1024`는 수십 ms라 연산은 병목이 아니지만 **JPEG 디코딩이 오래 걸립니다** — 장변 2048 기준 디코딩+EXIF 회전 **25~40ms**, 4032×3024 원본이면 **110~145ms**(W1 ①·② 실측, [`진행상황.md`](진행상황.md) §3.5). 데모에서 심사위원 여러 명이 동시에 촬영하는 상황이 실제 부하 시나리오입니다.

> **GPU 직렬화는 세마포어가 아니라 전용 스레드 1개로 합니다 (W1 ② 실측).** PyTorch는 **스레드마다 CUDA 초기화 비용을 따로 냅니다** — 어떤 스레드가 처음 추론할 때 약 810ms가 붙습니다. 세마포어로 직렬화하면 요청이 스레드풀의 여러 스레드에 흩어지므로 스레드마다 그 비용을 새로 내고, 무엇보다 **워밍업 스레드와 요청 스레드가 달라서 워밍업이 첫 사용자를 지켜 주지 못합니다**(워밍업 직후 단독 요청 815ms 측정). 동시 8건 실측: 스레드가 새것일 때 **5,702ms(1.4 req/s)** → 같은 스레드를 재사용할 때 **189ms(42 req/s)**. GPU 작업을 한 스레드에 못 박으면 그 비용을 워밍업에서 한 번만 내고, 직렬화는 구조로 보장됩니다(락이 필요 없습니다). JPEG 디코딩은 요청 스레드에 남겨 병렬로 둡니다.

**운영**

- **FP16 로드 + 프로세스 시작 시 워밍업 1회.** 첫 추론 **2~4초 → 2회차 43ms**(실측). 워밍업이 없으면 첫 사용자에게 타임아웃으로 나갑니다. 워밍업 전에는 `/healthz`가 `ready: false`(503)
- FP16 지정은 **`predict(quantize=16)`** 입니다 — `half=True`는 8.4.112에서 deprecated. 4070에서 **FP16이 지연을 줄이지는 않았습니다**(실측). VRAM 8GB에서 동시 요청 여유를 확보하는 용도로만 유지합니다
- **워커 1개.** GPU 하나를 여러 워커가 나눠 쓰면 VRAM만 낭비
- **`YOLO_AUTOINSTALL=false`** (코드에서 설정). ultralytics는 `PIL.Image.open`을 몽키패치해 두고 이미지 열기가 실패하면 HEIC일 수 있다고 보고 **요청 처리 중에 `pip install pi-heif`를 실행**합니다. 깨진 업로드 하나가 서버에서 pip를 돌리는 셈이고, `uv.lock`에 없는 패키지가 생기며 요청 경로에 네트워크 의존이 붙습니다 (W1 ②에서 실제로 당했습니다)
- **GPU 전원 관리**: 유휴 상태(14W)에서 온 첫 요청들은 클럭 램프업으로 느립니다 — 같은 사진이 138ms → 57ms로 내려갔습니다. 워밍업으로 해결되지 않는 종류라 NVIDIA 전원 관리를 최대 성능 우선으로 둬야 하는데, 이걸 처리하던 W1 ④가 폐기돼 **지금은 담당 지시 단위가 없습니다**
- **노출 경로는 ngrok 무료 dev 도메인입니다.** 계정마다 자동 배정되는 주소라 재시작해도 같습니다 — 고정 주소가 없으면 재시작마다 Spring 설정을 고쳐야 하고, 그게 데모 사고 1순위입니다. **배포 EC2에는 아무것도 설치하지 않습니다**(백엔드에 넘길 것은 주소 한 줄). 실행 명령·무료 한도·자동 기동은 [`진행상황.md`](진행상황.md) §3.1이 정본입니다
- **시크릿 헤더 검증.** 외부에 노출되는 순간 없으면 누구나 GPU를 씁니다
- ~~**자동 재시작 + 절전 해제 스크립트 2개**~~ — **W1 ④와 함께 폐기(08-02)**. `scripts/serve.ps1`(uvicorn+ngrok 한 쌍 관리, 강제 종료 시 13.5초 복구)과 `scripts/demo-prep.ps1`(작업 스케줄러 + 절전 해제)은 **삭제했습니다** — 되살리려면 `feature/ai/SH` 의 삭제 직전 커밋에서 꺼냅니다. **터널 쪽 자동 기동만 `ngrok service install` 로 되찾았습니다**(§9). uvicorn 재시작과 절전 해제는 대책이 없고, 터널이 서비스로 상주하는 만큼 **uvicorn 만 죽었을 때 빈 포트로 502 가 나가는 짝 문제는 오히려 더 잘 생깁니다** — serve.ps1 이 원래 막고 있던 것이 그것입니다
- **유선 연결**은 손으로 합니다. 캠퍼스 Wi-Fi 에 데모를 걸지 않습니다
- **한글이 든 `.ps1` 은 UTF-8 BOM 이어야 합니다.** PowerShell 5.1 은 BOM 이 없으면 ANSI(cp949)로 읽어 한글이 깨지고 **파서가 무너집니다** — 실행 실패가 아니라 구문 오류로 나타나서 원인이 안 보입니다
- TensorRT export는 이 규모에서 불필요

## 9. 데모 환경 체크리스트

AI 서버가 **노트북**이라 데모 당일 리스크가 구조적으로 높습니다. 기술이 아니라 운영에서 터집니다.

**한 번만 하는 설정**

- [ ] ngrok 계정 생성 → `ngrok config add-authtoken <토큰>`
- [ ] 대시보드에서 **배정된 dev 도메인** 확인 → `ai/.env`의 `NGROK_DOMAIN`
- [ ] `ngrok service install --config=<경로>` → `ngrok service start`. 터널은 부팅 시 스스로 뜹니다. **uvicorn 쪽은 여전히 대책이 없습니다**(§8 자동 재시작 항목)
- [ ] **유선 랜** 연결, 전원 연결
- [ ] NVIDIA 제어판 > 3D 설정 > 전원 관리 모드 = **최대 성능 우선** (GeForce는 `nvidia-smi` 전원 관리가 대체로 미지원이라 드라이버 UI에서 합니다)

**발표 당일**

- [ ] 서버가 떠 있는지 — 터널은 서비스로 이미 떠 있고 **uvicorn은 손으로 띄웁니다**(`uv run uvicorn app.main:app`). **터널만 살아 있고 uvicorn이 죽은 상태**면 ngrok이 빈 포트를 터널링해 백엔드가 **깔끔한 실패가 아니라 502**를 받습니다 — `UNAVAILABLE` 폴백은 작동하지만 원인이 안 보입니다(§8)
- [ ] `uv run python scripts/smoke.py --base-url <주소>` → **FAIL 0 · SKIP 0**. `SKIP` 은 통과가 아니라 **검사가 성립하지 않은 것**이고 종료 코드도 0 이 아닙니다 — 검출이 0개인 사진을 주면 항목·좌표 검사 5건이 빈 목록 위에서 통과해 버리므로, **쓰레기가 보이는 사진**을 `--image` 로 줘야 합니다
- [ ] `ready: true, warmedUp: true` 확인 후 첫 촬영
- [ ] **최후 안전망**: AI 서버가 죽어도 `UNAVAILABLE` → 수동 입력으로 줍깅 기록은 완주됩니다. 이 경로를 W5에 실제로 리허설해 두면 당일 사고가 데모 실패가 되지 않습니다

### 9.1 터널 너머에서 모델이 떴는지 확인하기

`/healthz`가 이 확인의 전용 창구입니다. **시크릿을 요구하지 않으므로** 주소만 알면 어디서든 칩니다.

```bash
curl https://<NGROK_DOMAIN>/healthz
```

| 응답 | 뜻 | 할 일 |
|---|---|---|
| `200` · `ready:true` · `warmedUp:true` | weights 로드·워밍업 완료 | 없음. 촬영해도 됩니다 |
| `503` · `error: "FileNotFoundError: weights 가 없습니다: …"` | **그 경로에 `.pt`가 없습니다** | `git pull`로 `weights/yolo26s-1024-v1.pt`를 받습니다 |
| `503` · `error: "RuntimeError: weights 의 클래스가 계약과 다릅니다 …"` | 파일은 있으나 7종·순서가 어긋납니다 | 학습 베이스(`yolo26s.pt`)를 잘못 지정한 경우가 대부분입니다 |
| `503` · `error: null` · `warmedUp:false` | 아직 워밍업 중입니다 (첫 로드 약 5초) | 기다립니다 |
| `502` — ngrok `ERR_NGROK_8012` | **터널만 살아 있고 uvicorn이 죽었습니다** | uvicorn을 띄웁니다 (§8) |
| `404` — ngrok `ERR_NGROK_3200` | 터널 자체가 떠 있지 않습니다 | `ngrok http 8000 --url=…` |

**`modelVersion`은 어느 파일이 로드됐는지 증명하지 않습니다.** 그 값은 파일에서 읽는 것이 아니라 `AI_MODEL_VERSION` 환경변수 문자열입니다(`app/config.py`). 실제로 로드된 파일명은 기동 로그의 `weights 로드 1.23s — yolo26s-1024-v1.pt` 한 줄에만 나옵니다 — **weights를 바꿔치기해도 `/healthz`는 같은 버전을 답합니다.**

계약 전체 확인은 스모크가 합니다. 같은 스크립트를 터널 주소에 그대로 겨눕니다:

```bash
uv run python scripts/smoke.py --base-url https://<NGROK_DOMAIN> --image <쓰레기가 보이는 사진>
```

**`FAIL 0`뿐 아니라 `SKIP 0`까지 봐야 합니다** — 검출이 0개인 사진을 주면 항목 검사 5건이 빈 목록 위에서 통과해 버리므로 SKIP으로 찍고 종료 코드를 0이 아니게 해 뒀습니다([`진행상황.md`](진행상황.md) §3.1).

### 9.2 주소는 두 파일이 같아야 합니다

앱은 이 주소를 모릅니다. **앱 → Spring → 터널** 순서라 ngrok 주소가 들어가는 곳은 `infra/.env` 한 곳뿐입니다(§1의 그림).

| 파일 | 키 | 값 |
|---|---|---|
| `ai/.env` | `NGROK_DOMAIN` | `<배정된-도메인>` — **배정값의 출처**. 스크립트가 읽지 않고 손으로 넘깁니다 |
| `infra/.env` | `AI_BASE_URL` | `https://<같은 도메인>` — **끝에 `/`를 붙이지 않습니다** |

두 값이 어긋나면 백엔드 호출이 **다른 터널로 갑니다.** 그 실패는 200 이외가 전부 `UNAVAILABLE`로 내려가므로 화면에서 "AI 서버 다운"과 구별되지 않고, 원인은 백엔드 로그에만 남습니다. 도메인을 바꿨을 때 **양쪽을 같이 고쳤는지**가 이 절의 전부입니다.

`AI_SECRET`도 두 파일이 같은 값이어야 합니다. 어긋나면 401인데, 위와 같은 이유로 증상이 구별되지 않습니다.

### 9.3 다른 노트북에서 서빙을 띄우기 — **주소를 유지한 채로**

먼저 이 두 가지를 알고 시작합니다. 모르면 주소가 바뀌거나 기동이 거부됩니다.

**① 주소는 ngrok 계정에 묶여 있습니다.** 무료 플랜은 **계정마다 dev 도메인 하나가 자동 배정**되고(동시 엔드포인트 3개까지), 그 계정의 authtoken을 넣은 에이전트만 그 주소로 뜹니다. 다른 계정으로 로그인하면 **주소가 달라지고**, 그러면 `infra/.env`의 `AI_BASE_URL`까지 고쳐 백엔드를 재배포해야 합니다. **주소를 그대로 쓰려면 옮길 것은 노트북이 아니라 authtoken입니다.**

**② 같은 주소로 두 번 띄울 수 없습니다.** 그 도메인에 이미 에이전트가 붙어 있으면 `ERR_NGROK_334`로 거부됩니다. 기기를 옮기는 것이라면 **옛 기기의 에이전트를 먼저 끊습니다** (`ngrok service stop`, 또는 띄워 둔 창을 닫습니다).

**③ 터널과 서버는 같은 기기여야 합니다.** ngrok 에이전트는 **자기 기기의** `localhost:8000`으로 넘깁니다. 노트북 A에서 터널을, B에서 uvicorn을 띄우면 A는 자기 8000에 아무것도 없어 `ERR_NGROK_8012`(502)를 냅니다.

```bash
# 1. 저장소 — dev 에서 시작합니다
git clone <저장소> && cd <저장소>/ai && git switch dev

# 2. 시크릿 — 없으면 서버가 아예 뜨지 않습니다(§8)
cp .env.example .env
#    AI_SECRET 을 채웁니다. 저장소에 없으므로 팀에서 받습니다.
#    배포 백엔드(infra/.env)의 AI_SECRET 과 같은 값이어야 합니다. 다르면 전부 401 입니다.
#    NGROK_DOMAIN 에는 배정받은 도메인을 적습니다(코드가 읽지는 않고, 아래 7번에 손으로 넘깁니다).

# 3. weights — 따로 받을 것이 없습니다. git 이 갖고 옵니다(§8)
ls weights/yolo26s-1024-v1.pt        # 20,350,405 bytes

# 4. 의존성
uv sync
uv run python -c "import torch; print(torch.cuda.get_device_name(0))"   # GPU 확인

# 5. ngrok 인증 — **주소를 유지하는 지점입니다.** 그 도메인을 배정받은 계정의 토큰이어야 합니다
ngrok config add-authtoken <토큰>

# 6. 서버 (워커 1개)
uv run uvicorn app.main:app

# 7. 터널 — 다른 창에서. `--domain` 은 deprecated 이므로 `--url` 을 씁니다
ngrok http 8000 --url=https://<NGROK_DOMAIN>

# 8. 확인 — §9.1
curl https://<NGROK_DOMAIN>/healthz
uv run python scripts/smoke.py --base-url https://<NGROK_DOMAIN> --image <쓰레기가 보이는 사진>
```

**4번에서 GPU 이름이 안 나오면 거기서 멈춥니다.** `pyproject.toml`이 torch를 **cu130 인덱스**에 고정해 두었고(서빙 노트북 드라이버 기준), 그보다 낮은 CUDA 드라이버에서는 GPU를 잡지 못합니다. 그 노트북에 맞는 인덱스로 바꾸고 `uv.lock`을 다시 만들어야 합니다 — CPU로 떨어진 채로 진행하면 추론이 수십 배 느려지고 데모에서 타임아웃이 됩니다.

**백엔드는 손댈 필요가 없습니다.** 주소를 유지하는 한 `infra/.env`도 재배포도 그대로입니다 — 앱이 보는 것은 백엔드 주소뿐이고, 터널 주소는 백엔드만 압니다(§9.2).
