### 3.2 클래스 경계 규칙 (§4.1)

**확정 (08-02, ⑥).** 기준축은 **시각 우선** — 사진 한 장으로 판정할 수 없는 구분은 만들지 않는다.
분리배출 규정과 갈리는 지점은 ⑦ 라벨링 가이드와 앱 안내 문구에 **각주**로만 남긴다.
규칙을 판정 문장으로 쓴 이유: 라벨러는 물건을 만져 볼 수 없다.

| 경계 | 판정 문장 | 상태 |
|---|---|---|
| `PLASTIC` ↔ `VINYL` | **"구겨서 놓으면 스스로 펴지는가?"** 펴지면 PLASTIC(성형품) · 안 펴지면 VINYL(얇은 막) | 확정 |
| `PLASTIC` ↔ `GLASS` | **"바닥이 두껍고 빛이 모서리에서 꺾이면 GLASS."** 눌린 자국·구겨짐이 있으면 PLASTIC — 유리는 안 눌린다 | 확정 |
| `PAPER` ↔ `GENERAL` | **겉면이 종이로 보이면 PAPER.** 코팅 여부는 묻지 않는다 — 종이컵·종이팩·기름 밴 피자박스 전부 PAPER. GENERAL 은 종이로 안 보이는 것만 | 확정 |
| `CIGARETTE` 범위 | **꽁초(필터+몸통)만.** 담배갑 → PAPER · 셀로판 → VINYL · 은박 → GENERAL. 전자담배·미개봉 담배 → GENERAL | 확정 |
| 부품 (뚜껑·팝탭) | **라벨된 본체 박스에 50% 이상 들어가면 박스를 치지 않는다.** 단독으로 떨어진 것만 본체와 같은 재질로 센다 — 안 그러면 페트병 1개가 `PLASTIC` 2개로 응답된다 | 확정 |
| 라벨하지 않을 것 | ① 알아볼 수 없을 만큼 흐릿한 것 ② 쓰레기가 아닌 것(낙엽·돌·설치물·차량·사람) ③ 프레임 경계에서 **절반 미만**만 보이는 것 ④ **용기에 붙은 뚜껑·캔따개** ⑤ 쓰레기통·봉투 **안에** 담긴 것 ⑥ 재질 판정 불가한 작은 투명 조각 | 확정 (⑦) |
| 박스 규칙 | 가려진 것은 **보이는 부분만**(추정 금지) · 겹친 꽁초는 **개별 박스** · **크기 하한 없음**(꽁초가 원래 작다) · 물체에 딱 맞게 | 확정 (⑦) |
| 애매할 때 | **라벨하지 말고 공유 → 주 1회 경계 사례 리뷰 → 확정되면 이 표에 한 줄 추가.** 각자 조용히 다르게 판단하는 것이 최악이다 | 확정 (⑦) |

### 3.4 전처리 위치 — 확정 (⑭, 08-06)

**리사이즈는 어디로도 옮기지 않는다.** 앱이 장변 2048 로 줄이고(결정 35) · 백엔드는 무가공 전달하고(§4.1 #2) · AI 서버는 letterbox 만 한다(README §3.1). **지금 구조 그대로이고 코드는 안 바뀐다.**

기준은 `(총 왕복 − inferenceMs) > 400ms 이면 옮긴다` 였고 실측 **473ms 로 넘겼는데도 안 옮긴다.** 그 기준이 "차이는 전송량 때문"이라는 전제로 쓰였는데 실측이 아니라고 말하기 때문이다 — **차이 ≈ 240ms + 0.15ms/KB** 로 **고정비가 지배한다**(§3.5).

| | 값 |
|---|---|
| 옮겨서 버는 것 | **153ms** (장변 2048 → 1024, 473 → 320ms) |
| 옮겨도 안 없어지는 것 | **240ms** — 터널 왕복 고정비. 빈 봉투도 이만큼 든다 |
| 대신 치르는 것 | 이중 보간 화질 손실(README §3.1 — **하필 꽁초 크기에서 드러난다**) · EXIF 보존이 명시적 요구사항이 됨 · 백엔드 CPU |

**이 판정의 제약 두 가지.** ① 클라이언트가 **EC2 가 아니라 SSAFY GPU 서버**다(EC2 SSH 키가 없다 — §5). ② 그래도 **방향은 안 흔들린다** — EC2 가 더 빠르면 473ms 가 내려가 안 옮길 이유가 커지고, 느리면 올라가지만 **버는 건 여전히 153ms** 다. 고정비가 클라이언트와 무관해서다.

### 3.5 실측값 — 지연·VRAM 은 RTX 4070 Laptop(서빙), 학습·지표는 H200(학습 서버). `imgsz=1024`

추측이 아니라 측정값이다. ⑭·⑰·⑳ 판단의 출발점으로 쓴다.

**`inferenceMs` — 입력 크기별** (서버 `/internal/infer` 왕복, 5회 중앙값. 네트워크 제외)

| 입력 | `inferenceMs` | 내부 분해 (디코딩 / 추론) |
|---|---|---|
| **1536×2048 — 앱이 보내는 크기**(장변 2048, 결정 35) | **110~140 ms** | 25~40 / 80~100 |
| 2048×1536 (장변 2048 가로) | 110~140 ms | 22~43 / 89~99 |
| 3024×4032 (앱 리사이즈 **전** 폰 원본) | **300~370 ms** | 82~134 / 202~254 |
| 3072×4096 (백엔드 거부선 직전) | 320~370 ms | 93~131 / 206~274 |
| 810×1080 (작은 샘플) | 25~40 ms | 4~11 / 20~30 |

'추론' 은 predict 전체 = letterbox(CPU) + 순전파(GPU) + 좌표 변환이다. 순수 GPU 시간은 약 20 ms 로, **연산은 제약이 아니다.** ① 에서 적었던 "폰 원본 200ms 대" 예상은 실측 **300~370ms** 로 정정한다. 다만 앱이 장변 2048 로 줄여 보내므로 **실제 경로는 110~140ms** 다.

**⑬ 이 이 표를 다시 확인했다 (08-06).** 모델을 COCO 사전학습에서 자체 학습본으로 바꿨으므로 값이 유효한지 봐야 했다 — 실제 경로(1536×2048) 5회 중앙값 **116ms** 로 위 범위 안이다. **⑭ 판단의 출발점은 그대로 쓸 수 있다.** (같은 측정에서 폰 원본은 190ms 로 표보다 낮게 나왔는데, GPU 클럭을 미리 올려 두고 JPEG 을 다시 인코딩해 재 값이라 위 행과 **비교 가능한 측정이 아니다** — 표를 고치지 않았다.)
