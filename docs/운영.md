# 운영

EC2 한 대 + Supabase Postgres + 담당자 노트북의 AI 서버. 컨테이너 4개(`기능범위.md` 인프라 행).

## 구성

```
인터넷 ─ Cloudflare(프록시) ─ EC2 nginx(:443) ─┬─ backend blue/green (:8080)
                                              └─ /ws  (소켓, 같은 backend)
backend ─ JDBC ─▶ Supabase Postgres (서울)
backend ─ redis (컨테이너)
backend ─ HTTPS ─▶ AI 서버 (담당자 노트북, ngrok)
```

- 공개 주소는 `www.gachi-joopging.site`. apex 는 Cloudflare 가 301 로 돌리므로 앱은 `www` 만 쓴다(POST 본문이 301 에서 사라진다)
- EC2 실제 IP 는 Cloudflare 뒤에 있다. `ssh gachi` 별칭으로 접속
- 컨테이너: `nginx` · `gachijoopging-blue` · `gachijoopging-green` · `acme` · `redis`

## 배포 — 반드시 `deploy.sh`

```bash
ssh gachi
cd /opt/gachijoopging/infra
./scripts/deploy.sh <IMAGE_TAG>
```

흐름: 현재 색 판별 → 새 색 기동 → readiness 통과 대기 → nginx upstream 전환 → 구 색 60초 drain 뒤 정지 → `.env` 의 `IMAGE_TAG` 갱신.
readiness 에서 실패하면 아무것도 바뀌지 않는다.

**`docker compose up` 으로 backend 를 직접 재생성하지 않는다.** nginx 가 옛 컨테이너 IP 를 물고 있어 502 가 나고, `.env` 의 옛 `IMAGE_TAG` 로 이미지가 조용히 되돌아간다. 컨테이너는 `healthy` 로 보여서 알아차리기 어렵다.

롤백: `./scripts/rollback.sh` — upstream 을 구 색으로 되돌린다.

이미지 빌드·푸시는 `./scripts/build-push.sh`(로컬). CI 는 이미지를 만들지 않는다.

## `.env` 키

실물은 EC2 의 `/opt/gachijoopging/infra/.env` 한 곳. 저장소에는 `infra/.env.example` 만.

| 키 | 용도 |
|---|---|
| `DOCKERHUB_USER` · `IMAGE_TAG` | 이미지 좌표. `IMAGE_TAG` 는 deploy.sh 가 갱신 |
| `PUBLIC_BASE_URL` | 서명 URL·메일 링크의 기준 |
| `DATABASE_URL` · `DATABASE_USER` · `DATABASE_PASSWORD` | Supabase 접속. 옛 `POSTGRES_*` 는 컨테이너용이라 없어진다 |
| `JWT_ACTIVE_KID` · `JWT_PRIVATE_KEY_PEM` · `JWT_PUBLIC_KEY_PEM` · `JWT_PREVIOUS_*` | 토큰 서명. kid 회전용 이전 키 |
| `KAKAO_REST_API_KEY` · `KAKAO_APP_ID` · `GOOGLE_CLIENT_ID` | 소셜 토큰 검증 |
| `MEDIA_SECURE_LINK_SECRET` | 사진 서명 URL |
| `MAIL_USERNAME` · `MAIL_PASSWORD` | 비밀번호 재설정 메일 |
| `FCM_CREDENTIALS` | 푸시 |
| `AI_BASE_URL` · `AI_SECRET` | AI 서버 |
| `CERT_DOMAIN` · `CERT_EMAIL` | acme |

없어지는 키: `LIVEKIT_*` · `GRAFANA_ADMIN_PASSWORD` · `ADMIN_WEB_TAG` · `POSTGRES_*`.

`.env` 를 고칠 때는 **바이너리로 다룬다.** PEM 값에 CR 이 섞이면 docker compose 는 통과시키고 Spring 만 `Missing key encoding` 으로 죽는다. Windows 편집기로 열지 않고 `dev-env.ps1` 같은 스크립트로 올린다.

## DB

- Supabase 프로젝트 대시보드가 곧 DB 모니터링이다. 연결 수·느린 쿼리·디스크를 거기서 본다
- 백업은 Supabase 자동 백업(일 1회). 옛 `backup.sh`(pg_dump → S3)는 필요 없다
- 스키마 변경은 Flyway 만. 대시보드 SQL 편집기로 스키마를 만지지 않는다
- 로컬 개발은 `infra/docker-compose.dev.yml` 의 PostGIS 컨테이너. 운영과 같은 16 + PostGIS

## 감시

모니터링 컨테이너가 없으므로 둘로 대신한다.

- 외부 헬스체크: 공개용 경로 하나를 5분마다 찌른다. 지금 있는 `actuator/health/readiness` 는 컨테이너 내부용이라 nginx 밖으로 열지 않고, 백엔드 정리 단계에서 `/api/v1/healthz` 를 만든다. 실패 알림은 팀 메신저로
- Supabase 대시보드: DB 쪽

장애 때 볼 순서: ① 헬스체크 응답 → ② `docker compose ps` 로 어느 색이 살아 있는지 → ③ `docker logs gachijoopging-<색> --tail 200` → ④ Supabase 연결 수 → ⑤ nginx 로그.

## 개인정보

- 위치 경로(`activities.route`)와 실시간 위치(`live_locations`)는 위치 정보다. 실시간 위치는 활동 종료 때 즉시 지운다
- 회원 탈퇴 때 개인 활동 상세(경로·사진 포함)를 지운다. 크루 합산은 `crew_daily_stats` 에 남는다(`ERD.md`)
- 사진은 서명 URL 로만 노출한다. 공개 버킷을 만들지 않는다
- 로그에 토큰·이메일·좌표를 남기지 않는다

## 스토어

- Android: `release.jks` 와 비밀번호는 저장소 밖(`local.properties`). 잃으면 덮어설치가 불가능하다
- iOS: 1차 범위 밖. 넣을 때 Apple 개발자 계정·서명·TestFlight 절차를 여기에 적는다
