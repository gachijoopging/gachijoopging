# 서버는 Lightsail VM 한 대에 docker compose 로 올린다

AWS Lightsail 서울 2GB 번들 한 대에 백엔드·Redis·Nginx 를 컨테이너로 띄운다. DB 는 Supabase(ADR-0001),
AI 는 담당자 개인 기기(지금은 M4 Mac mini)와 터널(`ai/README.md` §8)이라 서버에 올리지 않는다.

서버리스를 쓸 수 없다. 사진을 오브젝트 스토리지가 아니라 로컬 디스크에 두고 Nginx 가 직접 서빙하기로 했고,
Redis 가 상주해야 하며, 채팅·위치가 STOMP 소켓이라 WebSocket 을 종단해야 한다.
셋 다 꺼졌다 켜지는 실행 환경에서는 되지 않는다.

Lightsail 은 같은 사양에서 EC2 보다 싸고 단순하다. 디스크와 전송량이 번들에 들어 있어 월 $12 로 고정되는데,
EC2 는 인스턴스·EBS·공인 IPv4·전송량이 따로 붙어 두 배 가까이 되고 VPC·보안 그룹을 직접 만들어야 한다.
이 규모에서 그 유연성으로 얻는 것이 없다.

**스테이징을 두지 않는다.** 2GB 에 Spring 둘은 들어가지 않고, 두 번째 인스턴스를 사면 배포·시크릿·도메인·
인증서가 전부 두 벌이 된다. 3명이 2주에 만드는 규모에서 그 유지비가 스테이징이 잡아 주는 사고보다 크다고
봤다. `dev` 머지는 이미지를 만들어 레지스트리에 올리기만 하고, `main` 머지가 그 태그를 운영에 배포한다 —
배포되는 것은 CI 가 검증한 그 이미지 그대로다.

대신 서버에서만 드러나는 문제를 다른 데서 잡는다. 대소문자·빌드는 CI(Linux)가, 컨테이너 구성은 로컬
compose(GAC-100)가 본다. 그래도 남는 것 — 실제 도메인·인증서·소켓 프록시·2GB 메모리 한계 — 은 운영에서
처음 드러난다. 이것이 이 결정으로 치르는 값이다.

그래서 **서버 구축이 재현 가능해야 한다.** 설치 절차를 `infra/` 스크립트로 남겨, 지금 실험으로 더러워진
서버를 첫 사용자 전에 한 번 새로 만들어 교체한다. 그러지 않으면 왜 그렇게 설정됐는지 아무도 모르는 서버에
사용자가 올라앉고, 죽었을 때 복구할 수 없다.

## 고려한 대안

- **Oracle Cloud Always Free**: 비용이 0 이고 사양도 넉넉하지만 유휴 자원 회수 정책이 있고 SLA 가 없다.
  실사용자가 있는 서비스를 보장 없는 자원 위에 올리지 않는다. ARM 이라 CI 가 x86 러너에서 에뮬레이션으로
  빌드하는 비용도 매번 든다
- **EC2**: 천장이 높지만 지금 닿지 않는다. 요금이 항목별로 흩어져 예측이 어렵고 NAT 게이트웨이처럼 모르고
  켰다가 비싸지는 구석이 많다
- **PaaS(Fly.io·Railway)**: 볼륨과 Redis 를 애드온으로 붙이면 VM 보다 비싸진다

## 결과

단일 장애점을 받아들인다. 배포마다 짧게 끊기고 그 한 대가 죽으면 서비스가 멈춘다. 이중화 비용이 이 사용자
규모에서 회수되지 않는다. 대신 죽은 것을 늦게 아는 쪽이 더 위험하므로 감시를 먼저 건다(`operations.md` §감시).

옮길 때가 오면 스냅샷으로 EC2 에 내보낸다. DB 와 AI 가 서버 밖에 있고 나머지는 이미지 태그로 재현되므로
실제로 옮길 상태는 디스크의 사진뿐이다.

다시 열 조건: 디스크 50% · 동시 사용자 50 상시 초과 · Supabase DB 400MB. 사진을 로컬 디스크에 두는 결정이
가장 먼저 걸린다 — 서버를 두 대로 늘리려면 그것부터 오브젝트 스토리지로 옮겨야 한다.
