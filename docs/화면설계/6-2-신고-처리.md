# 6-2 신고 처리

**목적** 크루장이 대기 중인 신고를 확인하고 대상 삭제 또는 신고 기각으로 처리한다.
**원본** 신규 — `fragment_friends.xml`의 요청 목록과 `fragment_report.xml`의 사유 행을 재조립 · **변경** 옛 앱에는 크루장 신고 처리 흐름이 없었다. 신고 대상·사유·메모를 확인한 뒤 처리 결과를 결정한다.
**진입** 2-3 알림의 REPORT 대상 · **이탈** 뒤로 가기 → 2-3 또는 진입 화면

## 배치

가입 신청 관리와 같은 목록 뼈대(헤더 → 대기 수 → 행)를 따르되, 신고 행에는 대상 미리보기·사유·접수 시각과 처리 버튼을 둔다. 행을 누르면 같은 화면 안에서 상세 영역이 펼쳐지고 DELETE/DISMISS를 고른다.

```
┌──────────────────────────────────────┐
│ ① ‹  신고 처리                        │
├──────────────────────────────────────┤
│ ② 대기 중인 신고 1건                  │
│ ③ ┌────────────────────────────────┐ │
│    │ 상혁의 게시물                    │ │
│    │ "오늘 여의도..."                 │ │
│    │ 사유: 부적절한 사진 · 9월 2일     │ │
│    └────────────────────────────────┘ │
├──────────────────────────────────────┤
│ ④ 신고 내용                            │
│    신고자 지수 · 상세 메모 ...          │
│ ⑤ [기각]              [대상 삭제]      │
└──────────────────────────────────────┘
```

## 요소

| 구역 | 요소 | 내용 (계약 필드) | 컴포넌트 | 탭하면 |
|---|---|---|---|---|
| ① | 뒤로 버튼 | "뒤로" | `Icon`(arrow-left) | 2-3 또는 진입 화면 |
| ① | 헤더 제목 | "신고 처리" | `Txt` title | — |
| ② | 대기 수 | `GET /crew/reports`의 `items` 길이. "대기 중인 신고 1건" | `Txt` section | — |
| ③ | 신고 행 | `id`·`reporter.photoUrl`·`reporter.nickname`·`targetType`·`targetPreview`·`reason`·`memo`·`createdAt` (`GET /crew/reports`) | `Card` + `Avatar` sm + `Txt` + `Badge` | ④ 펼치기 |
| ③ | 대상 요약 | `targetType`별 "상혁의 게시물"·"상혁의 댓글"·"상혁의 크루 채팅 메시지"·"상혁". 본문 앞부분은 `targetPreview` | `Txt` body strong + `Txt` caption | — |
| ③ | 사유·접수 시각 | `reason`을 "스팸·도배"·"혐오·욕설"·"부적절한 사진"·"사생활 침해"·"기타"로, `createdAt`을 "9월 2일"로 표시 | `Badge` warning + `Txt` micro | — |
| ④ | 신고 상세 | `reporter.nickname`·`targetPreview`·`memo`. memo null이면 "상세 메모 없음" | `Card` + `Txt` | — |
| ⑤ | 기각 버튼 | "기각". 대상은 유지하고 신고만 처리 | `Button` ghost lg | 확인 대화상자 → `POST /crew/reports/{reportId}` (`result` DISMISS) |
| ⑤ | 대상 삭제 버튼 | "대상 삭제". USER 신고에는 숨긴다 | `Button` primary lg | 확인 대화상자 → `POST /crew/reports/{reportId}` (`result` DELETE) |

`targetType`이 POST·COMMENT·NOTICE_COMMENT·CHAT_MESSAGE이면 대상 삭제를 보인다. USER 신고는 이 API에서 DELETE할 대상이 없으므로 기각만 보이고, 크루원이 실제로 규칙을 어겼다면 크루장은 3-11 크루원 관리에서 추방한다.

## 상태

| 상태 | 보이는 것 | 눌리는 것 |
|---|---|---|
| 첫 진입 로딩 | ①은 보이고 ②·③ 자리에 `Loading` "신고를 불러오고 있어요" | ① 뒤로 |
| 새로고침 | 당겨서 새로고침. 기존 행은 남기고 상단 스피너 | 행·뒤로 |
| 빈 | `items`가 빈 배열. `EmptyState` "대기 중인 신고가 없어요" / "새 신고가 들어오면 여기에서 처리할 수 있어요." | 뒤로 |
| 오류 | `GET /crew/reports` 4xx·5xx면 `ErrorState` "신고를 불러오지 못했어요" / [다시 시도] | 다시 시도 |
| 오프라인 | 이전 행이 있으면 그대로, ② 아래 `Banner` "인터넷 연결을 확인해 주세요.". 없으면 오류 상태 | 이전 행·뒤로 |
| 권한 거부 | 크루원이 직접 진입하거나 403 FORBIDDEN이면 `ErrorState` "크루장만 신고를 처리할 수 있어요." / [크루 정보로] | 크루 정보로 → 3-2 |
| 부분 실패 | **해당 없음.** 목록 요청 하나다. 개별 처리 실패는 아래 행이 다룬다 | — |
| 처리 중 | 선택 행의 ⑤ 버튼 자리에 스피너. 다른 행은 비활성 | 없음 |
| 이미 처리됨 | 다른 기기에서 처리돼 404·409이면 행을 제거하고 `Snackbar` "이미 처리된 신고예요." | 나머지 행 |

기각 확인: "이 신고를 기각할까요?" / "대상은 그대로 유지되고 신고만 처리돼요." / [취소] [기각].

대상 삭제 확인: "신고 대상을 삭제할까요?" / "삭제한 게시물·댓글·메시지는 되돌릴 수 없어요." / [취소] [대상 삭제].

`POST /crew/reports/{reportId}` 204면 해당 행을 제거한다. DISMISS면 `Snackbar` "신고를 기각했어요.", DELETE면 `Snackbar` "신고 대상을 삭제했어요.". 4xx·5xx·오프라인이면 행을 유지하고 "신고를 처리하지 못했어요. 다시 시도해 주세요." `Snackbar`.

## 인터랙션

- 스크롤: 신고 행이 많으면 세로 스크롤. ④ 상세를 연 행은 펼친 채 스크롤한다
- 당겨서 새로고침: 있음. `GET /crew/reports` 재조회
- 길게 누르기: 없음
- 시트: 없음. 기각·삭제 확인은 대화상자
- 뒤로 가기: 2-3 또는 진입 화면으로 팝한다. 대화상자가 열렸으면 먼저 닫는다
- 키보드: 없음
- 신고 행 탭: ④를 펼치거나 접는다. 대상 원문·프로필로 이동하지 않는다. 신고 검토 중 차단 필터가 내용을 숨기면 안 된다
- 전환: 처리 성공은 목록에서 행만 제거한다. USER 신고 대상의 추방은 3-11로 별도 이동한다

## 접근성

- ②: "대기 중인 신고 1건"을 읽는다
- ③: "상혁의 게시물, 부적절한 사진, 9월 2일 접수, 신고 상세 보기"로 읽는다
- ④: 신고자·대상 인용·메모를 순서대로 읽는다
- ⑤: "신고 기각" / "신고 대상 삭제, 되돌릴 수 없음"으로 읽는다
- 모든 행·버튼은 44dp 이상이다

## 옛 화면과의 차이

- 옛 앱에는 크루장이 신고를 처리하는 화면이 없었다
- 친구 요청 목록의 행·처리 버튼 구조를 신고 대기 목록으로 재구성했다
- USER 신고는 대상 삭제 대신 3-11의 추방을 별도 행동으로 둔다

## 미결

- USER 신고 뒤 추방을 바로 제안할지, 신고 목록에서 3-11로 가는 링크를 둘지 계약·기능범위에 없다
- 처리 결과를 신고자에게 알림으로 보낼지 정책이 없다
- 신고 목록의 정렬 기준·처리 기한·자동 만료 정책이 없다
